# @packages/employeeJobPost

Folder: `packages/employee-job-post`. Matches: the `EmployeeJobPost` record that links an employee to a job post with its AI score, the matching step that creates these records after a crawl, and the API to browse, re-score, dismiss and subscribe to matches.

## What it does

`EmployeeJobPostService.match(jobs)` takes the new posts of a crawl, selects for each active employee the ones relevant to their criteria and minimum rate, scores each pair with `AiScoringService`, keeps the matches at or above `AI_MATCH_THRESHOLD`, saves them through `EmployeeJobPostCreateCommand`, publishes GraphQL subscription events and sends a Novu alert for scores at or above `NOVU_MATCH_NOTIFY_THRESHOLD`. `rematch(jobs)` does the same for posts that were already stored (found again, or re-offered by the `source-db` provider), limited to the employees whose criteria or profile changed since. An employee ↔ post pair gets at most one match. The resolver adds `browseJobMatches`, `rescoreMatch`, `dismissMatch` and two subscriptions to the generated CRUD.

## Why it exists

A job post is shared; whether it is a good match is per employee and per tenant. This package owns that judgment: the cheap keyword pre-filter and rate rule that limit AI calls, the AI score and its evidence, and the user-facing operations on a match.

## How it works

- `src/employeeJobPost.service.ts` — `EmployeeJobPostService` (`TenantAwareCrudService`):
  - `match(jobs)` — `EmployeeService.getActiveWithJobSearchCriteria()`; per employee `findRelevantJobs()` (jobs failing `hourlyRateFits()` are dropped; with active criteria a job must contain one of the criteria's `keyword` / `occupation` / `category` in its title, description, skills, search metadata, company, function or department; without criteria every active job passes); skip the posts the employee already has a match for (archived ones included; one `IN (...)` lookup per employee); in batches of 5: build the `EmployeeJobPost` (tenant and org from the employee; `createdAt` = when the match is stored), `scoreMatch()` → score fields and `modelUsed`, drop the pair below the threshold, save the match without AI fields when scoring fails; `commandBus.execute(new EmployeeJobPostCreateCommand(rows))`, which returns the rows really stored; `pubSub.publish('employeeJobPostCreated')` and `NovuService.sendMatchAlert()` (high scores) for those. Returns `{ created, unscored }`.
  - `rematch(jobs)` — for posts that were already stored. AI scoring stores nothing for a pair below the threshold, so evaluating every pair again on each crawl would score it again and again. Instead `rematchState` keeps, per employee, the content of their matching inputs (`matchingInputsFingerprint()`: name, bio, skills and experience summaries, preferred rate, job type and every criterion's id, keyword, occupation, category and status — what `findRelevantJobs()`, the rate rule and the scoring prompt read) and the stored posts already evaluated against it, rejected pairs included, whichever crawl brought them. A change is detected by the content, so one that leaves the timestamps as they were (a deleted criterion, a timestamp set some other way) counts too. The posts it concerns are those stored up to the change (they were matched against the former inputs when they were new): the time of the change is the newest stored timestamp of the employee and their criteria (the database stamps them; `ServerTimestamps*Hook` on GraphQL and `EmployeeService`'s REST writes keep clients from setting them; this process's clock is never compared) when that moved forward — inclusive, plus `REMATCH_TIMESTAMP_MARGIN_MS` (1 minute) for transaction start times and sub-millisecond precision — and otherwise every stored post. Timestamps that move forward without a content change (a reactivated employee, a change made and undone between two passes) extend the posts concerned to those stored meanwhile, while the pairs already evaluated are not scored again. A light query reads the posts' `createdAt` and whether they can be matched now (active, not archived, not expired); only those become candidates (an expired post that reopens is evaluated later), and they are loaded in full only when some pair is left to evaluate. Only the posts actually matched are marked as evaluated. Matching passes, new-post and re-match alike, run one at a time (one queue), and a new-post pass records the pairs it evaluated that a re-match could consider (posts stored before the employee's inputs last changed), so no pair is scored twice for the same inputs; every employee's branch settles before a failure is reported, and only completed employees mark their pairs as evaluated. The bookkeeping is in memory: after a restart, with nothing recorded, the posts stored before each employee's last stored timestamp are evaluated once more (once per process start); deleting or moving a criterion bumps the owner's `updatedAt` (hooks in `@packages/jobSearchCriteria`), so such a change also survives a restart. Matches already stored are not re-scored when the inputs change (`rescoreMatch` does that on request).
  - `browseMatches(args)` — tenant-scoped, filters `minScore` / `maxScore` / `budgetFit` / `recommendedAction` / `providerCode` / `isApplied`, sort by score or date, `first` / `offset`, returns `{ items, totalCount, hasMore }`.
  - `rescoreMatch(id)` — re-runs scoring on a match of the tenant and publishes `employeeJobPostUpdated`; `dismissMatch(id)` — archives it and publishes the same event.
- `src/rate-fit.ts` — the minimum-rate rule: `hourlyRateFits(job, minimumHourlyRateUsd)` is false only when the job is hourly (`isHourlyJob()`), its upper hourly bound (`hourlyRateUpperBound()`: structured `compensationMax`, else the rate or range advertised in the budget text) is known, is in USD and is below the employee's `preferredRate`.
- `src/commands/*`, `src/events/*`, `src/handlers/*` — `EmployeeJobPostCreateCommandHandler` inserts the rows with `ON CONFLICT DO NOTHING` against the unique index on (`employeeId`, `jobPostId`) in one transaction (one row per pair of the batch, chunks of 200, client-side ids to tell which rows were stored), then publishes `EmployeeJobPostCreatedEvent` for the stored rows and returns them; `EmployeeJobPostCreatedEventHandler` sends match alerts for rows carrying an `aiScore`; `MatchJobPostsToEmployeesCommandHandler` calls `match()` (saga, `JobPostCreatedEvent`) or `rematch()` (`{ existing: true }`, saga, `JobPostUpdatedEvent`), then enqueues the Trigger.dev task `score-matches` once, delayed by `PENDING_SCORING_DELAY` (5 minutes; limit: the unscored matches, at most `SCORE_PENDING_LIMIT`) when the pass stored matches without a score and `TriggerService.isEnabled()`.
- `src/resolvers/employeeJobPost.resolver.ts` — `EmployeeJobPostResolver`: nestjs-query CRUD on `EmployeeJobPostDTO`, `browseJobMatches(args)` (`src/dto/browseJobMatches.args.ts`, `.type.ts`), `rescoreMatch(id)`, `dismissMatch(id)`, subscriptions `employeeJobPostCreated(employeeId?)` and `employeeJobPostUpdated(employeeId?)` filtered by `matchEventFilter()` so a client only receives its own tenant's events.
- `src/employeeJobPost.controller.ts` — `@Crud` at `/api/employee/job`.
- `src/employeeJobPost.module.ts` — `EmployeeJobPostModule`: `CqrsModule`, `AiModule`, `TriggerModule`, repositories, `NestjsQueryGraphQLModule.forFeature` for `EmployeeJobPostDTO` (subscriptions and delete on), the handlers, `EmployeeService`, `JobPostService`, `NovuService`; exports `EmployeeJobPostService`. (`dashboardStats` is served by `DashboardResolver`, `@packages/dashboard`.)

## Wiring

- `AppModule` imports the module and lists it in the GraphQL `include`; `CrawlerModule`, `EmployeeJobApplicationModule`, `AutomationTaskModule` provide `EmployeeJobPostService` too.
- Environment variables (through `ConfigurationService`): `AI_MATCH_THRESHOLD` (default 60 in code, 70 in `.env.sample`), `NOVU_MATCH_NOTIFY_THRESHOLD` (80), `AI_SCORING_MODEL`, `OPENROUTER_API_KEY`.
- GraphQL: `employeeJobPosts`, `employeeJobPost`, `employeeJobPostAggregate`, `browseJobMatches`, `createOneEmployeeJobPost` … `deleteManyEmployeeJobPosts`, `rescoreMatch`, `dismissMatch`, subscriptions `employeeJobPostCreated`, `employeeJobPostUpdated`, `createdEmployeeJobPost`, `updatedOneEmployeeJobPost`, …
- REST: `/api/employee/job`.

## Using / extending

```graphql
query { browseJobMatches(employeeId: "…", minScore: 70, sortBy: SCORE_DESC, first: 20) { totalCount hasMore items { id matchScore recommendedAction jobPost { title url } } } }
subscription { employeeJobPostCreated(employeeId: "…") { id matchScore explanation } }
```

To change relevance, edit `findRelevantJobs()`; to change the rate rule, `rate-fit.ts` (both have focused specs). Matches saved without a score are picked up later by `OpsService.scorePendingMatches()`.
